# Changelog

All notable changes to Kairos are documented here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/). Each section comes from a closed ledger in `docs/roadmap/`, which holds the full detail and evidence. The Spanish version is [CHANGELOG.es.md](CHANGELOG.es.md).

Kairos has no tagged releases yet. Everything below is unreleased. The three components (server, kairos-mcp and the `@daycry/kairos` CLI) are at 0.4.0 and nothing has been published: the CLI is not on npm and no image is in a registry.

## [Unreleased]

### Added — `reliable-operations` initiative, milestone B (in progress)

- **Optional abstention in search.** `POST /v1/search` and the `search` tool accept an optional `abstain` boolean. With it on, the answer is `items: []` and `abstained: true` when the best semantic similarity is below the threshold of the embeddings model (`MEMORY_ABSTAIN_THRESHOLDS`, `model=threshold,...`) and no lexical layer returned anything; a degraded or truncated semantic layer, a lexical hit, a lexical layer that failed or ran out of time, or a model without threshold never abstains (the last adds `abstention: "uncalibrated"`). `MEMORY_ABSTAIN_DEFAULT` (`off` by default) sets what a request without `abstain` does. Without `abstain` the answer is exactly the previous one. The contracts only gain optional fields (`abstain`, `abstained`, `abstention`, also in `result_schemas.search`); calibrating `nomic-embed-text` on the 96-question evaluation set found no threshold with at least 70 % correct abstention and at most 5 % false abstention (0.60 gives 50.0 % and 2.8 %), so it stays `uncalibrated` and no threshold ships by default; the `retrieval-eval` gate now measures both rates. **Note for Iniciativa 7 (custom-agents):** `result_schemas.search` has `additionalProperties: false`, so a strict client built on the previous schema would reject `abstained`; abstention stays off by default (decision P-04) until that client consumes it, and turning it on changes what `custom-agents` sees (a search may answer `items: []`), so it should be decided together with that client; without a threshold per model an `abstain` request only adds `abstention: "uncalibrated"`. With `MEMORY_ABSTAIN_DEFAULT=on`, `POST /v1/context` and the `context` tool (they have no `abstain` of their own) also carry `abstained`/`abstention` and can return `context: ''` with no items.
- **A stuck queue is visible.** `/metrics` publishes `kairos_jobs_oldest_pending_seconds` (how long the oldest job that could already run has waited; 0 with an empty queue). `admin probe` compares it with `MEMORY_QUEUE_STUCK_SECONDS` (900 s by default) and, above it, logs `queue_stuck` and exits non-zero. The client side has its own check: `kairos doctor` reads the on-disk capture queue (read-only) and, when the oldest undelivered capture is older than `KAIROS_QUEUE_STALE_SECONDS` (900 s by default), reports `capture_queue_stale`, status `degraded` and **exits 1** (it used to exit 0). **Note for Iniciativa 7 (custom-agents):** a caller that treats a non-zero exit of `kairos doctor` as a failure will now see one for a stuck capture queue.
- **Round-trip probe.** `admin probe-provision` creates the `kairos-probe` project and a service account whose key can touch nothing else; `admin probe` writes a note, waits for its `embed` job, finds it by the semantic path, retires it, purges its rows and writes `kairos_probe_success` and the duration of each stage to a metrics file. The optional `memory-probe` service (profile `probe`) runs it every `MEMORY_PROBE_INTERVAL` seconds (300 by default) with a healthcheck on its own heartbeat; its searches always send `abstain: false`, so `MEMORY_ABSTAIN_DEFAULT=on` cannot make it fail. `docs/examples/prometheus-rules.yml` has example alerts (`KairosProbeFailing`, `KairosProbeSilent`, `KairosQueueStuck`, `KairosQueueScrapeBroken`, `KairosJobsFailed`); Kairos reads none of them and sends no notification itself.
- **Safer deployment and rollback.** `scripts/deploy-memory.py` takes a lock per project (a second deployment exits 3 with `deployment_locked`), tags the images in use before building (`<version>-<mark>`, the two newest kept) and `--rollback` goes back to those images without migrating (exit 4 `no_previous_images` if there is nothing to go back to, exit 5 `already_at_previous` if it already is). `apply` and `--rollback` also recreate `memory-probe` and `memory-backup` when they were running (an interrupted copy is dropped and made again in the next cycle), with the Compose files their container was created with (so `memory-backup` keeps the `rclone` override and its `egress` network); one created with other files, with no reliable label or (in an isolated rehearsal) without the rehearsal override is left running and the report says `*_recreate_skipped`; the console prints a command to run by hand with every `-f` of its label in order (plus the rehearsal override for a rehearsal container created without it), or, with no reliable label, with a `-f '<files it was created with>'` marker to replace (nothing is made up).
- **Limits and healthchecks.** Compose gives every service a memory limit and a CPU limit (`MEMORY_<SERVICE>_MEM_LIMIT`, `MEMORY_<SERVICE>_CPUS`, defaults in `docs/configuration.md`) and the long-running ones a healthcheck, and the Ollama proxy declares `extra_hosts: host.docker.internal:host-gateway` so the default `OLLAMA_UPSTREAM` also works on Linux.

**Action for existing installations:** `memory-backup` no longer joins the `egress` network. If your destination is `rclone:`, start it with `docker compose -f docker-compose.yml -f docker-compose.backup-rclone.yml --profile backup up -d memory-backup`; otherwise the copies stop being uploaded at the next `up`. A `dir:` destination needs nothing.

### Changed — `reliable-operations` initiative, milestone A (2026-11-15 to 2026-11-16)

Kairos no longer loses data or stops when the database does: copies are verified, encrypted and sent out of the machine on a schedule, the worker rides out a database outage, and the tables that only grow have a retention. [Ledger](docs/roadmap/2026-11-15-reliable-operations/tasks.md)

**Backups you can trust**

- **Verified copies.** Every copy has a manifest `<copy>.json` (sha256, size, schema version, time and per-table row counts and fingerprints). `admin verify-backup` detects an altered byte, a truncated copy or a missing or tampered manifest without decrypting anything. Manifests are format 2; copies of the earlier format are refused with `backup_manifest_format_unsupported` and need a new copy.
- **Encrypted copies.** With `MEMORY_BACKUP_RECIPIENTS_FILE` (public `age` recipients) the copy is encrypted as `<name>.age` and the dump in the clear never touches the disk; `MEMORY_BACKUP_REQUIRE_ENCRYPTION=1` refuses to write a plain copy. The private key never lives on the server: losing it means losing the copies. A decrypted dump is checked against the manifest of the encrypted copy with `admin verify-backup --manifest` or `admin restore-check --from-manifest`.
- **Retention of copies.** `admin backup --prune --keep N` verifies the N newest copies, deletes the older ones of its own name and never touches another file.
- **Safer deployment.** `scripts/deploy-memory.py` gives the copy, the content manifest and their verification a deadline (`--backup-timeout`, 3,600 s by default, up to 24 h) and can restore the previous copy into an isolated, ephemeral PostgreSQL and compare its tables with the manifest before migrating (`--verify-backup`; for an encrypted copy it only checks integrity).
- **Scheduled external copy.** `admin backup-cycle` (and the optional `memory-backup` service, profile `backup`, every 24 h) makes an encrypted copy, verifies it, sends it to a directory (`dir:<path>`) or an `rclone` remote (`rclone:<remote>:<path>`), reads it back there, and applies the retention of both places. Only encrypted copies leave the machine, and it refuses to start without recipients. Any failure of the cycle (an invalid setting at start and a failed local retention included) sets `kairos_backup_offsite_success` to 0 in `kairos-offsite.prom`, logs `backup_offsite_failed` or `backup_cycle_failed`, keeps every local copy and retries on the next cycle. Its database and `pg_dump` connections time out when connecting and use TCP keepalives (a half-open connection fails the cycle instead of hanging the service), and `rclone` retries the upload. The destination must belong to one installation.
- **Restore runbook.** [Operations](docs/operations.md) has the step-by-step restore, with the private key outside the server, and `scripts/rehearse-restore.py` rehearses it end to end in an isolated project until the restored tables equal the manifest.
- **Closing of the milestone.** A refused start of `backup-cycle` also sets the metric to 0; a failure of only the local retention logs `backup_cycle_failed`; a copy changed after it was verified is never sent (it is checked and uploaded from the same open file, without following links; `rclone` receives it with `rcat`). `scripts/rehearse-reliable-operations.py` rehearses, in an isolated project, the restore, the measure of the fingerprints and a stop and start of the database with the worker running.

**A server that rides out a database outage**

- **The worker waits instead of dying.** When the database stops answering it waits with growing pauses (up to `MEMORY_WORKER_DB_BACKOFF_MAX`, 60 s by default), logs `store_unavailable` and takes the queue up again when the database is back. A result it cannot save is kept and written again (up to `MEMORY_WORKER_WRITE_RETRY_SECONDS`); an outage longer than the lease can cost the attempt. A database error is now told apart from a provider failure (`store_error`).
- **A job that cannot finish stops being retried for ever.** A job whose worker dies without stopping is no longer claimed once it uses `MEMORY_MAX_ATTEMPTS`: it ends `failed` with `attempts_exhausted` and `POST /v1/jobs/{id}/retry` revives it. An invalid `MEMORY_MAX_ATTEMPTS` or `MEMORY_LEASE_SECONDS` stops the startup.
- **Connection pool and deadlines.** API and worker reuse connections from a pool (`MEMORY_POOL_MIN`/`MAX`/`TIMEOUT`, 1/10/5 s) and use connection and statement deadlines and TCP keepalives (`MEMORY_CONNECT_TIMEOUT`, `MEMORY_STATEMENT_TIMEOUT_MS`, `MEMORY_TCP_*`). A query that hangs is cancelled by the server. `MEMORY_CONNECT_TIMEOUT` and `MEMORY_POOL_TIMEOUT` must differ by at least 1 s (the service refuses to start otherwise). A warm pool opens no new connection per search.
- **Clear errors.** A database that answers too slowly gives 503 `store_timeout`, a saturated pool 503 `store_busy` and an outage 503 `service_unavailable`, each with a fixed message and a `request_id`; search never answers 200 with a partial result for these. `/health/ready` stays 200 with a full pool and gives 503 only when the pool never delivered a connection.
- **Permissions per transaction.** Permissions are read once per transaction: a revoked key, user, session or grant stops working from the next request, also after waiting for a lock (ingest, publish, delete and retry answer 401/403). A hybrid search makes 14 fewer queries (63 to 49 with the pool).
- **Faster job claim.** Claiming a job no longer walks and sorts everything pending: with tens of thousands queued it goes from about 110 ms to under 1 ms. Two partial indexes (schema version 12) are added without touching rows or columns.

**Tables that no longer grow for ever**

- **`admin prune-tables [--dry-run]`.** Deletes old rows in batches from `login_attempts` (30 days), expired or revoked `web_sessions` (30), `audit_events` (365) and orphan failed jobs (90: no receipt, not cited by a kept event and not the current version of a document or note), by the `MEMORY_RETENTION_*_DAYS` windows. Nothing runs it on its own; `backup-cycle --prune-tables` can run it at the end of each cycle. `events` is **not** pruned unless you set `MEMORY_RETENTION_EVENTS_DAYS`; each real run leaves a `retention_prune` row in `audit_events`. Pruned orphan jobs answer 404 on `GET /v1/jobs/{id}` and retry; the MCP contract is unchanged.

Migrations are additive and `docs/contracts/kairos-mcp.json` is unchanged. Everything new is for the operator; clients only see the 503 codes, `attempts_exhausted`, `store_error` and the pruned jobs described above.

### Changed — `three-components` initiative (2026-11-12 to 2026-11-14)

Kairos is split into three components: the server, kairos-mcp and the CLI, plus the web portal. The server no longer needs a language model. [Ledger](docs/roadmap/2026-11-12-three-components/tasks.md) · [final review](docs/roadmap/2026-11-12-three-components/review.md)

- **Three components in one repository.** The server lives in `server/` (the Python package is still `memory_platform`, built with `server/memory_platform/Dockerfile`), kairos-mcp in `mcp/`, the CLI in `client/` (was `packages/kairos-cli/`) and the portal image in `web/` (`web/Dockerfile`, `web/nginx.conf`). Compose keeps the same services, names, volumes and networks; only the build paths changed. `npm pack` of the CLI lists the same files. Server, kairos-mcp and CLI are all 0.4.0.
- **No extraction in the server by default.** `MEMORY_EXTRACT_ENABLED` is `0`: an event with `generate: true` (the CLI sends it with summaries) is accepted with 202 and creates no `extract` job. The receipt gains an additive `extraction: "disabled"` field. Jobs already queued are kept and marked `extraction_disabled`; `POST /v1/jobs/{id}/retry` queues them again once extraction is on.
- **`corpus_answer` is off by default.** `MEMORY_CORPUS_ANSWER=off` keeps the tool in the list of 34 and rejects a new request with `corpus_answer_disabled` without calling any provider (repeating a saved `request_id` returns the saved answer while `MEMORY_LLM_MODEL` is unchanged, or a conflict if the request or the model differs); `corpus_answer_status` still reads saved answers.
- **No default model.** `MEMORY_LLM_MODEL` has no value any more; turning on extraction or generated answers without it stops the startup with a message that names the variable. An installation that relied on the previous default must set it.
- **A closed Ollama proxy.** The internal proxy only forwards `/api/embed` and `/api/version`; everything else gets 403 from the proxy. `OLLAMA_ALLOW_CHAT=1` also allows `/api/chat`. The proxy no longer runs as root.
- **`/mcp` now goes to kairos-mcp.** The web proxy (`127.0.0.1:5173/mcp/`, the address `kairos mcp` uses) serves kairos-mcp instead of the server's own MCP, and `memory-web` joins the internal `mcp` network and waits for `memory-mcp`. The CLI bridge needs no change; the differences a client sees (Bearer credential only, `structuredContent` in 12 tools, a 401 without `X-Request-ID`) are in [integration](docs/integration.md#conectar-con-kairos-mcp).
- **The internal MCP is deprecated and goes in 0.5.0.** It stays at `memory-api:8790/mcp/` through 0.4.x with `Deprecation: true` and `Sunset: 0.5.0` on every response and one `mcp_legacy_used` log event per call (method, status and request id, nothing else). `MEMORY_MOUNT_MCP=0` unmounts it and `/mcp` answers 404; the default is `1`. Migration notes: [integration](docs/integration.md#migración-el-mcp-interno-queda-en-desuso-y-se-retira-en-la-050) and [operations](docs/operations.md#retirada-del-mcp-interno).
- **kairos-mcp, a container of its own.** The 34 MCP tools are served by `memory-mcp` (`mcp/`), which has no database access: it calls `/v1` with the caller's Bearer, wraps read results as untrusted data and publishes the same tools and contract as before (`docs/contracts/kairos-mcp.json` only gains `x-kairos-*` keys and `structured`).
- **A REST `/v1` endpoint for every MCP tool.** Each tool has a `/v1` counterpart with the same permissions, so any HTTP client can do what the MCP tools do.
- **Versioned observation and session-summary schemas.** `docs/contracts/observation.v1.schema.json` and `session-summary.v1.schema.json`, with valid and invalid examples checked by the tests.
- **Continuous integration.** Six GitHub Actions jobs (server, retrieval-eval, mcp, client, web, contracts) run on every push and pull request, read-only and with actions pinned by SHA.
- **Deployment check of `/mcp`.** `scripts/deploy-memory.py` checks `/mcp` with a temporary read key that it revokes at the end (the portal session no longer reaches kairos-mcp), says on the console when `/mcp` was not checked, and can run an isolated rehearsal with a simulated embedding provider (`--embed-stub`, `--roundtrip`). After updating, recreate the `ollama` service too: its template now uses `OLLAMA_ALLOW_CHAT`.

### Changed — `retrieval-quality` initiative (2026-11-09)

Search is now measurable and finds more of what you stored. [Ledger](docs/roadmap/2026-11-09-retrieval-quality/tasks.md) · [final review](docs/roadmap/2026-11-09-retrieval-quality/review.md)

**Search quality**

- **Retrieval evaluation.** A frozen synthetic dataset of 72 questions (Spanish, English, typos, long documents) and a `retrieval-eval` gate measure recall@k and MRR per layer and subset, offline. Combined search went from recall@5 0.50 and MRR 0.34 to 1.00 and 0.97. With the real `nomic-embed-text` model it reaches 1.00 and 0.99.
- **pgvector and HNSW.** Semantic search runs in PostgreSQL with pgvector instead of cosine similarity in Python. An HNSW index covers the indexed model, and exact SQL cosine covers the rest, with the same permissions and time limits. The PostgreSQL image is now a derived image with a pinned pgvector version.
- **Language-aware full-text search.** Notes, documents, facts, agent corpora and portal filters ignore accents and match word forms in Spanish and English (`canción`/`canciones`, `failed`/`fails`). When few results come back, `pg_trgm` adds near matches for typos and identifiers such as `ERR-4471`, marked as approximate.
- **Chunking for long texts.** Documents and notes are split into chunks of about 1,500 characters with 200 of overlap. Search now finds content past the old 8,000-character cut, and results carry an optional `matched_chunk` with the passage that matched. `admin backfill-chunks` prepares existing content and runs during deployment.
- **Hybrid search by default, with degradation.** If only the semantic layer fails, search and context still return the lexical results and say so in an optional `degraded` field (`timeout`, `provider_error`, `store_error`, `no_vectors`, `embeddings_disabled`). An optional `semantic_budget_ms` caps the time spent on the semantic layer.
- **Tunable fusion.** "Validated" is now a tunable bonus in the combined ranking (`MEMORY_FUSION_VALIDATED_BONUS`), no longer an absolute order. `MEMORY_FUSION_K` and `MEMORY_FUSION_WEIGHTS` are configurable too.

**Operations**

- **Structured logs.** The API and the worker write one-line JSON logs with level, event, duration and request id. Secrets are redacted, every previously silent failure leaves a trace with its exception type, and third-party libraries never log below INFO.
- **Prometheus metrics.** `GET /metrics` exposes search-layer latency, provider errors by code, job queue depth, failed jobs by code and embedding-slot saturation, all with closed label values. It answers only on the internal network, or with admin credentials, or not at all (`MEMORY_METRICS`), and nginx and Caddy never publish it.
- **Additive migrations up to schema v11.** These add the `vector` extension, `unaccent`, `pg_trgm`, per-language columns, the `memory.embedding_chunks` table and a partial index on failed jobs. A test now fails if any migration drops or rewrites existing data.
- **Deployment rehearsal.** `scripts/deploy-memory.py` can run an isolated rehearsal project. The full activation (migration, vector and chunk backfill, verification) was rehearsed end to end with identical content and an empty queue at the end. The real deployment moves to Initiative 5 of the [master plan](docs/roadmap/2026-11-10-platform-audit/plan.md).
- **Manuals.** The architecture, configuration, operations, integration and user manuals cover all of the above, and every new variable is listed and passed through Compose.

**Clients and contract**

- **MCP contract.** Additive changes only: the optional `matched_chunk`, `degraded` and `semantic_budget_ms`. All 34 tools keep their contract.
- **CLI 0.3.0 (unpublished).** Automatic context also uses semantic search, within a 1.1 s budget, and accepts the server's `degraded` notice.

**Known limits**

- With the real embedding model, one of 12 long-document questions ranks second instead of first (`ca18:long`). This is accepted as debt; the fusion will be tuned against the real model in Initiative 5.

### Added — earlier initiatives (2026-11-04 to 2026-11-06)

These ledgers predate the current format and `changelog-sync` cannot read them, so this summary follows their checklists.

- **Native product (`native-product`, 2026-11-04).** Kairos becomes a standalone repository with a native API and worker on PostgreSQL. It adds private work state per actor and project, 23 MCP tools, a "My work" view, a dependency-free Node installer, a deployment flow with backup and MCP verification, its own manuals and exported contracts. The MCP tools were accepted in real Claude Code, Codex and OpenCode clients. [Ledger](docs/roadmap/2026-11-04-native-product/tasks.md)
- **Automatic memory per client (`automatic-memory`, 2026-11-05).** Native client events are captured automatically, with privacy applied before anything is stored. A recoverable outbox, a local dispatcher over authenticated loopback IPC (hooks never call the remote server) and bounded, authorized context injection complete the flow. The installer merges hooks without removing other configuration. Accepted in Claude, Codex and OpenCode. [Ledger](docs/roadmap/2026-11-05-automatic-memory/tasks.md)
- **Functional workflows (`functional-parity`, 2026-11-06).** This adds local code search, outline and symbol expansion with explicit exclusions and limits. It also adds named observation writes and tool-use retrieval, and shared team work separate from private lists. Generated corpus answers come with token budgets and checked citations, and there are observation, rule, work and activity views. Registry publication of the package is still pending. [Ledger](docs/roadmap/2026-11-06-functional-parity/tasks.md)
